# Contributing — как команде обновлять документацию

> Правила работы с базой знаний Seller Exchange (внутр. **AmazonService / AS**).
> Философия — в [MANIFESTO](MANIFESTO.md), структура — в
> [INFORMATION_ARCHITECTURE](INFORMATION_ARCHITECTURE.md).

## Источники правды (raw) — не редактируем через КБ

База знаний строится поверх материалов проекта. Их правим в первоисточнике,
затем отражаем в КБ:

| Источник | Что даёт |
|---|---|
| `Obsidian Vault/wiki/` | Продуктовая wiki: функционал, роли, дизайн-система |
| `Obsidian Vault/ФУНКЦИОНАЛ/`, `ИНТЕРФЕЙС/`, `РОЛИ/` | Сырые макеты и заметки |
| `platform-routes.md` | Роуты, компоненты, 117 модалок, таблицы |
| `platform-mockups-index.md` | Индекс макетов |
| `platform_tables_figma_mapping.md` | Привязка таблиц к Figma |
| `figma-mcp/docs/Data filters *.md` | API `data_filters`: фильтруемые колонки, видимость данных по роли (инженерная — в КБ только продуктовая выжимка) |
| `figma-mcp/sources/mhtml/*.mhtml` | Захваты экранов (`Role-Screen.Theme.Lang.mhtml`) — **визуальный источник** для Screen Guides вместо скриншотов (light/dark, En/Uk/Ru/Ua) |

> При расхождении между дизайн-именами и кодом (напр. Freelancer ↔ Service
> Provider) — фиксируй оба и помечай `⚠️`, не «исправляй» молча.

## Прежде чем писать

1. Проверь, нет ли уже статьи (правило «один факт — одно место»).
2. Определи раздел по [INFORMATION_ARCHITECTURE](INFORMATION_ARCHITECTURE.md).
3. Если это термин / экран / сценарий — сначала заведи запись в
   [GLOSSARY](GLOSSARY.md) / [SCREEN_CATALOG](SCREEN_CATALOG.md) /
   [WORKFLOW_CATALOG](WORKFLOW_CATALOG.md) и получи ID.

## Как создать статью

1. Скопируй [ARTICLE_TEMPLATE](ARTICLE_TEMPLATE.md).
2. Заполни шапку: `owner`, `created`, `review_by`, `audience`, `related_*`.
3. Пиши по [STYLE_GUIDE](STYLE_GUIDE.md).
4. Свяжи термины, экраны, сценарии ссылками (не копируй).
5. Поставь `status: draft`.

## Жизненный цикл статьи (`status`)

```
draft ──▶ review ──▶ published ──▶ (устарела) ──▶ review/archived
```

| Статус | Значение |
|--------|----------|
| `draft` | В работе, автор пишет |
| `review` | На вычитке, готова к проверке |
| `published` | Опубликована, актуальна |
| `archived` | Выведена из обращения (не удаляем сразу) |

## Ревью

- Каждая статья проходит ревью до `published`.
- Ревьюер проверяет: точность, соответствие [STYLE_GUIDE](STYLE_GUIDE.md),
  корректность ссылок и ролей, отсутствие реальных ПДн на скриншотах.
- Ревьюер и автор — разные люди.

## Актуальность

- У каждой статьи есть `owner` и `review_by`.
- По наступлении `review_by` владелец сверяет статью с продуктом и
  продлевает дату либо правит.
- Изменение продукта → сначала правим источник правды (глоссарий/каталоги/
  матрицу), затем зависящие статьи.

## Локализация

- Переводим только `published`-статьи по [LOCALIZATION_GUIDE](LOCALIZATION_GUIDE.md).
- Правка источника переводит все локали в `status: review`.

## Именование и структура

- Файлы статей — `kebab-case.md`; переводы — `name.<lang>.md`.
- Идентификаторы `WF-###`, `SCR-###` стабильны и не переиспользуются.
- Глубина вложенности — до 3 уровней.

## Release Notes

- Значимые изменения фиксируются в разделе Release Notes
  ([INFORMATION_ARCHITECTURE](INFORMATION_ARCHITECTURE.md) §8) с датой `YYYY-MM-DD`.

## Быстрый чек-лист PR/правки

- [ ] Нет дублирования, есть ссылки на источники правды.
- [ ] Шапка заполнена, `status` выставлен.
- [ ] Термины/экраны/сценарии заведены в каталогах.
- [ ] Прошло ревью вторым человеком.
- [ ] Скриншоты без реальных данных клиентов.
